# Trading logic — how Jarvis actually decides to trade

This is a reverse-engineered map of the real decision path, with file:line references, current as of the codebase on 2026-08-14. If you change the scoring/risk code, update this doc in the same PR — it's the thing future-you (or Claude) will trust instead of re-reading five files.

## 1. Signal generation — `services/screener_service.py`

For any symbol, `scan_symbol()` (`screener_service.py:167`) builds a composite `signal_score` from 9 independent sub-scores, each computed from a separate service module and summed (`screener_service.py:235-246`). **Note**: the module docstring calls this a "0-100" score, but the nine factor maximums actually sum to **130** (15×8 + 10 for MACD) — this is a real discrepancy in the code, not a documentation error here. It doesn't break anything (the STRONG BUY/BUY/WATCH thresholds below are just thresholds against whatever the sum produces), but don't assume 100 is the ceiling when reasoning about "how close to maxed out" a score is, and don't silently "fix" it to sum to 100 without checking whether recalibrating the 75/60/45 thresholds is intended — that would change every historical STRONG BUY/BUY classification's meaning.

| Factor | Function | Max pts | What earns full marks |
|---|---|---|---|
| Volume spike | `_volume_score` | 15 | volume_ratio ≥ 3.0x average |
| RSI zone | `_rsi_score` | 15 | RSI 45-65 (trending, not overbought) |
| Bollinger position | `_bollinger_score` | 15 | price at/near lower band (mean-reversion buy zone) |
| Candlestick pattern | `_candlestick_score` | 15 | 2 bullish patterns (Hammer, Morning Star, etc.) in last 6 candles |
| MACD | `_macd_score` | 10 | MACD > signal line AND histogram positive |
| SMA trend | `_sma_trend_score` | 15 | price above SMA20/50/200 + golden cross (SMA50 > SMA200) |
| Elliott Wave | `_elliott_score` | 15 | end of Wave 2 (Wave 3 starting) — the single highest-weighted individual condition |
| Trendline breakout | `_trendline_score` | 15 | confirmed breakout with volume; breakdowns score 0 (bearish, irrelevant to a BUY screen) |
| Fundamentals | `_fundamental_score_contribution` | 15 | yfinance-derived fundamental_score ≥ 75; unknown/unavailable fundamentals default to a neutral 5, not 0 |

**Classification** (`screener_service.py:251-258`):
```
score >= 75  → STRONG BUY   (the only signal the scheduler will auto-trade)
score >= 60  → BUY
score >= 45  → WATCH
else         → NEUTRAL
```

**Trade suggestion** (only computed for BUY/STRONG BUY, `screener_service.py:263-296`):
- Stop-loss = `max(entry * 0.97, nearest_support * 0.995)` — whichever is *tighter is not chosen*; it takes the max, i.e. the wider of the two floors, biasing toward the support level when one exists below price.
- Target = `min(entry * 1.08, nearest_resistance * 0.998)`.
- Trade is only surfaced if **R:R ≥ 1.5**; otherwise no `trade_suggestion` is attached even though the signal itself is BUY/STRONG BUY.
- `trade_type` = INTRADAY if RSI > 68, else SWING — this is the only place trade_type is decided, and it's a side-effect of RSI, not of which scan (premarket/intraday/swing) triggered it.

There is no ML model anywhere in this path — every number above is a deterministic rule. `services/claude_service.py` runs *after* this and only produces a narrative explanation; its output (`signal/confidence/target/stop_loss/risks`) is shown in the frontend's AI panel but never fed back into `screener_service` or `trading_service`. If Claude's API key is missing or the call errors, it silently falls back to a canned "HOLD/LOW confidence" object (`claude_service.py:164-167`) — a bad model id or auth failure will not surface as an error to you, just a bland fallback.

## 1a. Short-selling — an intraday-specific strategy, not a mirror (added 2026-08-13, redesigned 2026-09-22)

`scan_symbol()` computes a **second, independent composite score in the same pass** — no extra broker/data calls — for the bearish side (`screener_service.py`, each factor named `_xxx_score_short`). Fundamentals are reused unchanged (`_fundamental_score_contribution`, still capped at a neutral 5 for intraday scans since `include_fundamentals=False` there); there's no separate "weak fundamentals" bearish scorer — intraday shorting is a technical, not fundamental, decision.

**Originally this was a straight mirror of the LONG scorers** (same weights, signs flipped) — a 2026-09-22 strategy review found that assumption doesn't hold ("up the stairs, down the elevator": declines are faster and more distribution-driven than the grind-higher pattern that rewards a momentum-long approach) and rebuilt four of the nine factors to be genuinely short-specific instead. Everything below is computed by `_compute_short_bias_metrics(df)` (called once per scan, feeding the rewritten scorers) and is **only ever read by the short-side code path** — none of it touches `technical_service.compute_indicators()` (shared by both directions) or any LONG-side scorer.

| Factor | Function | What earns full marks |
|---|---|---|
| Volume | `_volume_score_short` | **Rewritten.** Requires both an elevated `volume_ratio` *and* a majority of the last 5 candles' volume occurring on down (red) candles (`down_volume_ratio`) — confirms distribution, not just any spike. A stock scoring full marks on the old shared `_volume_score` could do so on a volume spike that happened on a green candle; this can't. |
| RSI | `_rsi_score_short` | **Rewritten.** `rsi_rolled_over` (RSI touched ≥65 in the last 10 bars and has since dropped to ≤55 — rejected from overbought, now breaking down) is the top-scoring case. The old static "RSI currently 35-55" check remains as a smaller fallback, not the primary signal — two stocks reading RSI 45 today (one just rejected from 75, one just bounced off 20) no longer score identically. |
| Bollinger position | `_bollinger_score_short` | unchanged — price at/near **upper** band (overbought, mean-reversion down) |
| Candlestick pattern | `_candlestick_score_short` | unchanged — bearish patterns (Shooting Star, Evening Star, Three Black Crows, Dark Cloud Cover, bearish Engulfing) |
| MACD | `_macd_score_short` | unchanged — MACD < signal AND histogram negative |
| SMA trend | `_sma_trend_score_short` | unchanged — price below SMA20/50/200 + death cross (SMA50 < SMA200) |
| Elliott Wave | `_elliott_score_short` | **Weight reduced** (15/12/12/10/3 → 8/6/6/5/2). Elliott Wave is a swing/position technique reading multi-day wave structure; applying it at full weight to 15-minute intraday bars (the only timeframe short signals are ever scored on) was a timeframe mismatch. Kept as a secondary factor, not removed — same wave-direction-checking logic as before. |
| Trendline breakdown | `_trendline_score_short` | unchanged — confirmed BREAKDOWN with volume; breakouts score 0 |
| **VWAP** | `_vwap_score_short` | **New.** Price below today's session VWAP (cumulative typical-price×volume ÷ cumulative volume, reset at the first bar of each trading day) scores; at/above scores 0. The standard intraday professional reference level — appropriate for a same-day strategy in a way Elliott Wave isn't, which is most of why Elliott's weight moved here. |

Same `>=75/60/45` classification thresholds as before — left uncalibrated deliberately, since there's no real trade history yet to justify moving them (short-selling has produced zero executed trades since launch; see the "why redesign a strategy with no track record" note below).

**Short trade suggestion** (only for SELL/STRONG SELL) — **stop/target sizing rewritten 2026-09-22**: previously a flat 3%/8% off entry, mirrored from the LONG SWING formula, applied to **100% of short trades** because shorting is always intraday (below). An 8% move in a liquid large/mid-cap NSE name within one session is rare — the stop was realistically reachable, the target mostly wasn't, so the nominal "R:R ≥ 1.5" overstated what was actually achievable in a day. Now: `stop_loss = entry + max(1.0 × ATR(14), entry × 0.8%)` (`SHORT_SL_ATR_MULT`, `SHORT_SL_MIN_PCT`), `target = entry - min(1.8 × ATR(14), entry × 5%)` (`SHORT_TARGET_ATR_MULT`, `SHORT_TARGET_MAX_PCT`, all named constants in `screener_service.py`) — scales to each stock's own recent volatility instead of a blanket percentage, with the 5% ceiling keeping the target realistic for a single session (was 8%) and the 0.8% floor preventing a noise-width stop on very low-ATR names. Still compared against the nearest resistance/support level exactly as before (tighter SL / nearer target wins); falls back to the old flat-% behavior only if ATR is unavailable (insufficient data) — never a harder failure than pre-redesign behavior. **`trade_type` is always `INTRADAY`** — unlike the LONG side, there's no SWING short: retail can't carry a cash-equity short overnight in India (no delivery to give on settlement).

**Why redesign a strategy with a zero-trade track record?** Because the flaws were identifiable from the strategy logic itself, independent of trade history: mirroring long-side weights, scoring undirected volume, reading RSI level instead of trajectory, and sizing an intraday-only target off swing-style percentages are all structural issues visible by reading the code, not just things a backtest would have caught. The alert *gate* (requiring `STRONG SELL` + a live confirmed breakdown on the same candle, separately identified as the reason zero trades have fired at all) is untouched here — that's enrichment #8, a distinct, not-yet-approved change.

**Where it surfaces**: only `job_intraday_scan` (every 15 min, 09:30-15:15) queues SHORT signals — no premarket or swing short-selling, matching the INTRADAY-only constraint above. Alert gate mirrors the LONG side's STRONG BUY+breakout gate exactly: requires `short_signal == "STRONG SELL"` **and** a live BREAKDOWN trendline signal (`scheduler_service.py`'s `job_intraday_scan`), not just a high score alone.

**Safety guard — never short a symbol you're already holding**: before generating SHORT candidates, the scheduler filters out any symbol currently in `trading_service.get_state().positions` (long *or* short). This is a UX-level filter (avoids wasting an alert on something that would just get rejected); the real enforcement is one layer down in `enter_trade()`'s pre-existing "Already in position for {symbol}" check, which is direction-agnostic and fires regardless of this filter. Practically: if a stock you're long in becomes a strong short candidate, nothing happens until that LONG position's own SL/target/EOD exit clears it — only on a *later* scan tick, once the symbol is no longer held, can a fresh SHORT signal be queued for it.

**SHORT-specific entry guard** (`trading_service.py:409`): `enter_trade()` rejects outright — before any broker call — if `direction == "SHORT"` and either `trade_type != "INTRADAY"` or `product != "MIS"`. This is enforced twice: `signal_service.approve_signal()` already forces `trade_type="INTRADAY", product="MIS"` for any SHORT signal before calling `enter_trade()`, and `enter_trade()` itself re-checks and rejects rather than silently correcting — a caller passing SHORT+CNC is treated as a bug worth surfacing, not papered over.

**Mechanically**: `Position.direction`/`ClosedTrade.direction` already supported `"SHORT"` before this — `enter_trade()` places a **SELL** order to open (`tx_type = "BUY" if direction == "LONG" else "SELL"`), `exit_trade()` places a **BUY** order to cover. Position sizing (`calculate_position_size`) is unchanged and already direction-agnostic (`risk_per_share = abs(entry - stop_loss)`). `exit_all_intraday()` (3:15 PM square-off) already filtered only by `trade_type == "INTRADAY"`, not direction — so it already correctly covers SHORT positions at EOD with no changes needed there.

## 2. Risk management — `services/trading_service.py` + `config.py`

Four env-driven gates, all defined in `config.py:76-81`:

| Env var | Default | Enforced where |
|---|---|---|
| `TRADING_CAPITAL` | ₹100,000 | base for all % calculations |
| `MAX_RISK_PER_TRADE_PCT` | 2% | `calculate_position_size()` (`trading_service.py:213`) |
| `MAX_PORTFOLIO_EXPOSURE_PCT` | 60% | caps position size in the same function, *and* re-checked as a hard gate in `can_enter_trade()` |
| `DAILY_LOSS_LIMIT_PCT` | 3% | `can_enter_trade()` (`trading_service.py:234`) |
| `MAX_OPEN_POSITIONS` | 5 | `can_enter_trade()` |

**Position sizing** (`trading_service.py:calculate_position_size`):
```
risk_amount   = capital * (MAX_RISK_PER_TRADE_PCT / 100)
shares        = risk_amount / abs(entry - stop_loss)
max_deployable = capital * (MAX_PORTFOLIO_EXPOSURE_PCT / 100) - already_deployed_capital
shares        = min(shares, max_deployable / entry)
shares        = min(shares, broker.get_available_funds() / entry)   # 2026-07-23
```

**Real available funds are a hard cap, not a replacement for `TRADING_CAPITAL`** (added 2026-07-23, `brokers/base.py`'s `get_available_funds()` — Zerodha via `kite.margins()["equity"]["net"]`, Fyers via `fyers.funds()`). Sizing is still driven by the configured `TRADING_CAPITAL`/risk-%/exposure ceilings above; the live broker balance only ever *shrinks* the result, never grows it past the configured ceiling — so having more cash sitting in the account doesn't silently increase risk per trade, but having *less* than `TRADING_CAPITAL` assumes will correctly reduce (or zero out) position size instead of getting a broker rejection for insufficient funds. If the funds API call itself fails (network blip, margins endpoint down), sizing silently falls back to the configured-capital-only calculation — this fails open to the pre-2026-07-23 behavior, not closed.

**`_state.capital` going stale silently strangled sizing — fixed 2026-08-06** (`_effective_capital()`, `trading_service.py:235`). `_state.capital` is a manually-set persisted snapshot (`trades.json`, see §"State" below), not a live figure — it only changes when someone edits it. Twice in production, a stale snapshot combined with real deployment growth pushed `deployment_pct` right up against `MAX_PORTFOLIO_EXPOSURE_PCT`, leaving so little "allowed" headroom that `calculate_position_size()` zeroed out *every* new trade regardless of signal quality (once: capital said ₹14,039.80 while the account actually held ₹15,880.60 after a real position had been deployed since). Fix: both `calculate_position_size()` and `can_enter_trade()`'s exposure check now use `max(_state.capital, broker.get_available_funds() + _state.deployed_capital)` as the basis — i.e. never *less* than the saved snapshot, but self-corrects upward toward the real current account size (free cash + capital already deployed) instead of requiring a manual refresh every time real funds change. A funds-fetch failure falls back to the saved snapshot exactly as before — no worse than pre-fix behavior. **Note**: `portfolio_summary()`'s *displayed* `capital`/`deployment_pct` fields still reflect the raw saved snapshot unchanged — this fix only changed the gating math, not the reporting figures, so the two can legitimately show different numbers; that's intentional; the display value is a historical audit figure (MTD/QTD % are computed off it too), not a real-time gate.

**Estimated quantity preview** (`estimate_quantity()`, `trading_service.py:300`): every pending signal (email/WhatsApp/Signals tab) shows how many shares the sizing formula would actually buy *right now*, computed once at signal creation (`signal_service.add_pending_signal()`) so all display surfaces agree. Runs the exact same `calculate_position_size()` math used at real approval time — a true preview, not an approximation. If real broker funds can't be fetched (not authenticated, API error, or a genuinely empty account), falls back to a clearly-labeled **hypothetical ₹10,000 balance** (`HYPOTHETICAL_CAPITAL`, `trading_service.py:297`) rather than silently showing 0 shares — this fixed figure is deliberately unrelated to `TRADING_CAPITAL` and never persisted anywhere.

**Rejection reasons stay visible after the fact — added 2026-09-21** (`_position_size_breakdown()`, `trading_service.py`; `signal_service.list_recent_resolved()`; `GET /api/signals/recent`). Real incident: a user approved a signal, it got rejected with `"Position size is 0..."`, and the only way to explain *why* was manually reconstructing the math from server logs (deployed capital, live broker funds, the 60% exposure cap). `calculate_position_size()` is now a thin wrapper around `_position_size_breakdown()`, which keeps every intermediate number (effective capital, deployed capital, max deployable, shares-from-risk/exposure/funds) instead of collapsing straight to a share count. `enter_trade()` attaches this breakdown to the result under `sizing_breakdown` whenever it rejects for a zero-size reason. Resolved signals (approved *or* rejected *or* expired — not just pending ones) stay queryable via `GET /api/signals/recent`, reusing `signal_service`'s existing in-memory `_pending` store rather than a new persistence layer. The frontend's **Recent Decisions** panel (`frontend/src/components/RecentDecisions.tsx`, below the Signals tab's pending queue) renders this as a plain-language table — "your total money," "already tied up," "room left" — instead of raw field names, so a rejection is understandable without asking anyone to explain it.

**Important limitation**: all four gates are checked **only at trade-entry time** (`can_enter_trade()`, called from `enter_trade()`). They are not re-evaluated continuously. `monitor_positions()` (`trading_service.py:402`, called every 15 min by the scheduler) checks each open position's own SL/target/trailing stop, but does **not** re-check `DAILY_LOSS_LIMIT_PCT` as a circuit breaker mid-day — if unrealized losses on open positions deepen between scheduler ticks, nothing forces an exit until either that position's own SL is hit or someone tries to open a *new* trade (which is when the daily-loss gate would then block further entries).

**Trailing stop** (`monitor_positions()`, `trading_service.py:421-439`): activates once a position is +5%, trails 3% below the running peak (LONG) or above the running trough (SHORT); it only ever tightens in the favorable direction, never loosens.

**Partial profit-taking at target — added 2026-07-29** (`_partial_exit_target()`, `trading_service.py:589`; gating in `Position.should_exit()`): the first time a position's target is hit, only **half** the quantity is closed — booked as a `ClosedTrade` with `exit_reason="PARTIAL_TARGET_50PCT"` — and the remaining half keeps running, with its stop-loss moved up to breakeven-or-better (LONG: `max(stop_loss, entry_price)`; SHORT: `min(stop_loss, entry_price)`) and the trailing stop armed immediately at the current price. `Position.partial_exit_done` flips to `True`, and `should_exit()` then stops treating the *original* target as an exit trigger for the remainder — the runner is governed purely by its (now breakeven-protected) stop-loss and the trailing stop from that point on, so it isn't capped at the first target. If the position is too small to split (`quantity // 2 == 0`), falls back to a normal full exit instead. This is the mechanism behind "lock in half, let the rest run risk-free."

**Entry-time additional gate** (`routers/trading.py:92-100`, mirrored inside `enter_trade()` at `trading_service.py:270`): R:R must be ≥ 1.5 or the order is rejected before it ever reaches the broker.

State (`Position`, `ClosedTrade` dataclasses) lives in a module-level singleton, persisted to `backend/data/trades.json` after every mutation (`trading_service.py:322, 384, 448`) and reloaded on process start. There is no database and no integrity check on that file — a manually edited or corrupted JSON silently becomes "reality" for open positions on next load.

**Trade Book / reasoning fields — added 2026-07-28** (`Position`/`ClosedTrade`, `trading_service.py:60-65, 123-127`): both dataclasses carry `signal_score`, `source` (`PREMARKET`/`INTRADAY`/`SWING`/`MANUAL`), `reason` (the breakout description or a score summary, whichever `approve_signal()`/the Research tab's approve action supplied), `risk_amount` (₹ actually at risk = `quantity * |entry - stop_loss|`), and `capital_at_entry` (`_state.capital` at sizing time, so the 2%-risk math is auditable after the fact) — plus `partial_exit_done` (see above). All default to `0.0`/`"MANUAL"`/`""`/`False` so pre-existing `trades.json` entries from before these fields existed still load without a migration. The frontend's **Trade Book** tab (`frontend/src/components/TradeBook.tsx`, wired into `App.tsx`) reads these directly off `GET /api/trading/positions` and `/history` to show *why* each trade was taken, not just its mechanics — this is deliberately scoped to trades Jarvis itself identified and you approved, never pre-existing holdings placed outside the app.

## 3. Automation timeline — `services/scheduler_service.py` (IST, Mon–Fri)

| Time | Job | What it does |
|---|---|---|
| 08:30 | `job_auto_login` | Scripted Zerodha web-login via stored password + live TOTP code (see `docs/SECURITY.md` §Zerodha auto-login) |
| 09:00 | `job_premarket_scan` | Full watchlist + fundamentals, `min_score=60`, top 5 emailed **and** queued to `signal_service` for approval in the Signals tab, TTL until today's 15:15 close |
| 09:15–15:15, every 15 min | `job_intraday_scan` | 1) `monitor_positions()` first (SL/target/trailing checks on existing positions) 2) scans top 15 watchlist symbols on 15-min candles 3) **for the top 3 results, if `signal == STRONG BUY` AND there's a confirmed trendline breakout**, it alerts **and** queues to `signal_service` (`scheduler_service.py:144-166`), TTL 20 min — no order is ever placed automatically; entering the trade requires approving it in the Signals tab or a separate, human-initiated call to the trading API |
| 15:15 | `job_exit_intraday` | Square off all MIS/INTRADAY positions before close |
| 15:35 | `job_daily_report` | P&L summary via email/WhatsApp |
| 15:45 | `job_swing_scan` | EOD scan, `min_score=65`, top 3 emailed **and** queued to `signal_service` for next-day entry, TTL ~24h |

**No job in this file ever calls `enter_trade()` directly.** Every candidate any scan finds — premarket, intraday, or swing — goes through the same human-approval gate in the Signals tab (`services/signal_service.py`, `routers/signals.py`); only `approve_signal()` bridges into `trading_service.enter_trade()`, and that only runs when you click Approve. The three scan types differ only in *how long* a signal stays valid before expiring unapproved (20 min / until close / ~24h) and which `trade_type` (INTRADAY→MIS vs SWING→CNC) the resulting order uses.

## 4. Order execution — `brokers/zerodha.py` / `brokers/fyers.py`

`trading_service.enter_trade()` → `_get_broker()` picks Zerodha or Fyers per `ACTIVE_BROKER` → `broker.place_order(order_type="LIMIT", price=limit_price)`. Both brokers place **live orders directly**; there is no paper/simulation broker class. `dry_run=True` is a parameter on `enter_trade()` (surfaced via `POST /api/trading/dry-run`) that returns the computed sizing without calling the broker — it is not a global switch, so every other call path is live by default.

**Not a true market order** (fixed 2026-07-23): Zerodha's API rejects plain `MARKET` orders outright — *"Market orders without market protection are not allowed via API. Please set market protection or use a Limit order."* This was silently failing **every single approval** from 2026-07-22 until the fix (order placed, immediately rejected, `EXECUTED` never returned — `approve_signal()` correctly reported the `ERROR` status, but it's easy to miss in the UI). The fix: `enter_trade()` now fetches live LTP via `broker.fetch_ltp()` at approval time and places a marketable `LIMIT` order priced `LIMIT_ORDER_BUFFER_PCT` (0.25%, `trading_service.py`) beyond it — above LTP for BUY, below for SELL — snapped to the correct tick size via `_round_to_tick()`. This fills essentially immediately in normal liquidity while satisfying the API's requirement. The position's stored `entry_price` is this computed limit price, not the original signal's (possibly stale — up to ~24h old for swing) `entry_price`; if the LTP fetch itself fails, it falls back to the signal's entry price.

**Tick size is per-symbol, not universally 0.05 — fixed 2026-08-13** (`_tick_size_for()`, `trading_service.py:346`; `BaseBroker.get_tick_size()`, `brokers/base.py:36`; `ZerodhaBroker.get_tick_size()`, `brokers/zerodha.py:67`). Every LIMIT price above used to snap to a hardcoded 0.05 — but NSE sets tick size per-security, and SBIN in particular ticks in **0.10**. This silently rejected every SBIN approval from Aug 11 onward with *"Tick size for this script is 0.10. Kindly enter price in the multiple of tick size for this script"* — same silent-`ERROR` failure mode as the MARKET-order bug above. Fix: `ZerodhaBroker.get_tick_size()` reads the real per-symbol `tick_size` field already present in Kite's own instrument master (`kite.instruments()`, cached alongside the existing `instrument_token`/`name` lookup used by `get_instrument_token()` — no new API call, just one more field carried through from data already being fetched). `BaseBroker` ships a `0.05` default so Fyers (which doesn't override it) is unaffected. All three LIMIT-pricing call sites (`enter_trade`, `exit_trade`, `_partial_exit_target`) fetch the real tick size per symbol via `_tick_size_for()`, which falls back to `0.05` if the lookup itself fails — no worse than the pre-fix behavior.

**A failed exit used to fail silently — fixed 2026-08-19.** Real incident: NTPC hit its stop-loss on Aug 14 and Zerodha rejected the SELL order 93 times over 5 trading days with *"shares need to be authorised at CDSL (your demat depository) to sell"* — a CDSL/SEBI requirement for delivery (CNC) sells that needs a one-time DDPI (Demat Debit and Pledge Instruction) authorization on the broker account; not something the app can complete on your behalf. The dangerous part wasn't the rejection itself, it was that `job_intraday_scan`'s logging (`scheduler_service.py`) declared `"Position exited: NTPC — STOP_LOSS"` on **every single failed retry**, based only on `should_exit()` having fired — it never checked whether `exit_trade()`'s result actually said `CLOSED`. The position sat unprotected the entire time with no signal anything was wrong. Fixed two ways: (1) `exit_trade()` and `_partial_exit_target()` now call `alert_service.alert_exit_failed()` (`alert_service.py`) on every failed broker order — deliberately noisy (fires on every retry, not just the first) since silence is exactly what caused the 5-day gap; (2) the scheduler's log line now checks the actual `result["status"]` before claiming success, logging `ERROR`-level "Exit FAILED... still open" otherwise (`scheduler_service.py`, `job_intraday_scan`).

Order lifecycle sync happens via broker webhooks: Zerodha → `POST /api/auth/postback`, Fyers → `POST /api/auth/fyers/postback`. Both are public (unauthenticated by API key, since brokers can't send it) — the Zerodha handler now verifies Zerodha's HMAC checksum before trusting the payload (fixed — see `docs/SECURITY.md`); the Fyers handler is still a stub that only logs (`routers/auth.py:326-337`, literally commented "Future: parse and sync"). Neither postback reconciles `trading_service`'s in-memory state beyond a P&L log line — the source of truth for "am I in a position" remains `trades.json`, updated only by the code paths in `trading_service.py` itself, not by broker callbacks.

## 5. Zerodha auth — two distinct flows, different risk profiles

1. **Official OAuth** (`routers/auth.py:32-163`): `/login-url` → browser login → Zerodha redirects to `/api/auth/callback?request_token=...` (public path) → `KiteConnect.generate_session()` exchanges it for an access token. Standard, documented, revocable.
2. **Scripted auto-login** (`services/auto_auth_service.py`): POSTs your stored `ZERODHA_USER_ID`/`ZERODHA_PASSWORD` to `kite.zerodha.com/api/login`, then a TOTP code computed live from the stored `ZERODHA_TOTP_SECRET` (raw base32 seed, via `pyotp`) to `/api/twofa`, then follows Kite Connect's `login_url()` under that now-authenticated web session to capture `request_token`, then completes the same `generate_session` exchange. This automates against Zerodha's **internal, undocumented web endpoints**, not the Kite Connect API — see `docs/SECURITY.md` for why storing the TOTP seed is materially riskier than storing a password alone (the seed lets anyone with it generate valid 2FA codes indefinitely, i.e., it *is* your second factor, not a credential protected by one).

Access tokens for both brokers live only in `Settings._kite_access_token` / `_fyers_access_token` — class-level, in-memory, gone on every process restart. That's why both the startup task (`main.py:41-53`) and the 08:30 job exist — Fyers has no equivalent auto-refresh, so a Fyers session lost to a restart requires manual re-auth.

## 6. Where the frontend actually reaches

The React SPA (`frontend/src`) has three tabs:

- **Research** (`GET /api/stock/{symbol}` — chart + indicators + candlestick patterns + FII/DII + AI narrative). Since 2026-08-13 it's no longer purely read-only: `TradeSetupCard.tsx` additionally calls `GET /api/scanner/symbol/{symbol}` (the same composite-scoring engine from §1, on-demand for *any* symbol you look up, not just the fixed watchlist) and `POST /api/trading/dry-run` for a live quantity preview, with its own **Approve & Enter** button that calls `POST /api/trading/enter` directly — bypassing the Signals-tab pending-signal queue entirely, since you're already looking at the app in real time. `POST /api/trading/enter` optionally accepts `signal_score`/`source`/`reason` (defaults `0.0`/`"MANUAL"`/`""`) so these manual approvals still land in the Trade Book with real provenance instead of a blank entry.
- **Signals** (`GET/POST /api/signals/*` — the pending-approval queue described in §3, with Approve/Reject actions and a live favicon/tab-title badge). Also reachable via one-click email/WhatsApp links (`GET /api/signals/email-action/{id}/{approve|reject}`, token-authed — see `docs/SECURITY.md`).
- **Trade Book** (`GET /api/trading/portfolio` / `/positions` / `/history`) — the reasoning fields described above, plus win rate and realized P&L.

`GET /api/trading/broker/funds` (added 2026-08-06) exposes the same live-margin figure `calculate_position_size()` already caps against, for checking it directly without triggering a trade. The broader scanner/trading surface beyond what's listed above still has no dedicated page — exists in `api/client.ts` but unused. Full picture in `docs/ARCHITECTURE.md`.
